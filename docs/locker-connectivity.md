# Locker connectivity

The backend subscribes to `lockers/{device}/heartbeat` and `lockers/{device}/status`. A heartbeat or `online` status marks the locker online. A `status` payload of `offline` marks it offline immediately; firmware should configure that message as its MQTT Last Will. Live door status messages also refresh `LastSeenAt`; retained door messages are ignored because they do not prove the device is currently connected.

`LockerMonitoring:Enabled` defaults to `true`, enabling stale-connection detection and door-open alerts. Set `LockerMonitoring:OfflineAfterSeconds` above the firmware heartbeat interval (minimum 10 seconds; default 90). The worker checks every 5 seconds and marks a locker offline after the cutoff. A newly registered locker uses `Unknown` until its first signal and becomes `Offline` after the cutoff. Firmware must send a periodic heartbeat and an offline Last Will before device acceptance; a publish acknowledgement alone does not prove the door opened. Restart the backend after changing worker settings.

The unlock safety guard always rejects `Offline` and `Unknown` connection states with HTTP 409 `locker/offline`, including operator emergency opens. Setting `LockerMonitoring:Enabled=false` disables background monitoring and door-open alerts only; it cannot bypass the connection guard. This override is intended for isolated development environments, and does not establish device readiness. No shared runtime configuration is changed by the source default; hardware heartbeat/Last Will and alert acceptance remain separate verification steps.

On a connection change, the backend writes `LockerEvent.ConnectionChanged` and publishes `LockerConnectionChanged` through OperationsHub. Offline transitions also create in-app notifications for assigned active operators, or active administrators if no operator is assigned. Remote unlocks return HTTP 409 with code `locker/offline` when connection status is not online.
